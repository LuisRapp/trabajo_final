## Casos de Usos Reales

Esta fase documenta el diseño de los flujos más representativos del sistema. Se profundiza en primer lugar en los **tres procesos automatizados** (PA-01, PA-02, PA-03, definidos en el Documento de Requisitos), que constituyen el corazón operativo: flujos que corren solos, disparados por tiempo, evento o cambio de estado. Para los casos de uso críticos disparados por actores humanos, los diagramas de secuencia de diseño (10 UC críticos con aplicación de patrones GRASP) se encuentran en `DIAGRAMAS_SECUENCIA_DISENO.md`.

***\<Interface Gráfica\>: Mantenimientos + campana de notificaciones + Estado de procesos (Administración)\>***

&nbsp;

| PA-01&nbsp; | Mantenimiento preventivo por umbral de producción |  |
| :---- | :---- | :---- |
| **Objetivos asociados**&nbsp; | OBJ-03 Gestión del mantenimiento y control de costos de maquinaria; OBJ-07 Seguridad y auditoría funcional |  |
| **Requisitos asociados**&nbsp; | RF-20; IRQ-02; IRQ-09; IRQ-10; UC-62; UC-63; UC-67 |  |
| **Descripción**&nbsp; | El sistema acumula toneladas por maquinaria con cada carga registrada (odómetro, en tiempo real) y, en una verificación diaria, genera automáticamente la orden de mantenimiento preventivo al superarse el umbral, con personal asignado, fecha fuera de la ventana de lluvia, detección de stock del kit y avisos por canal interno y email. |  |
| **Precondición**&nbsp; | Cron del servidor activo; existen maquinarias operativas con umbral configurado y tipo preventivo. |  |
| **Secuencia normal**&nbsp; | **Paso**&nbsp; | **Acción**&nbsp; |
| &nbsp; | 1 | (Tiempo real) Al registrarse una carga en el parte diario se dispara el evento CargaRegistrada; el listener ActualizarOdometroMaquina incrementa el odómetro de la maquinaria. |
| &nbsp; | 2 | (Diario 06:30) La tarea programada mantenimiento:check-umbrales recorre las maquinarias operativas. |
| &nbsp; | 3 | Calcula las toneladas desde el último mantenimiento cerrado (snapshot) y las compara con el umbral. |
| &nbsp; | 4 | Saltea idempotentemente las maquinarias que ya tienen orden abierta. |
| &nbsp; | 5 | Resuelve la fecha programada con los datos climáticos del proceso PA-02, evitando la ventana de lluvia de 72 horas (fallback: día siguiente). |
| &nbsp; | 6 | En transacción: crea la orden (estado programado), asigna personal disponible (rol mantenimiento → administrativo → sin filtro), detecta faltantes del kit preventivo, crea propuesta de compra si corresponde y crea la notificación interna (umbral_alcanzado) a los usuarios configurados. |
| &nbsp; | 7 | Tras el commit: envía email con PDF de orden (y compra) con reintentos ante rate-limit. |
| &nbsp; | 8 | (Cada 4 horas) mantenimiento:check-programados envía recordatorios de órdenes de hoy y marca como vencidas las no confirmadas, creando la notificación interna (mantenimiento_vencido). |
| **Postcondición**&nbsp; | Órdenes generadas con personal y avisos; propuesta de compra ante faltantes; vencimientos marcados y notificados. El cierre humano (UC-62) registra el snapshot que reinicia el ciclo. |  |
| **Excepciones**&nbsp; | **Paso**&nbsp; | **Acción**&nbsp; |
| &nbsp; | 6 | Si falla el procesamiento de una maquinaria: rollback de su transacción, registro del error y continuación con la siguiente. |
| &nbsp; | 6 | Sin personal disponible: la orden se crea sin asignación y se registra el aviso. |
| &nbsp; | 7 | Si el email falla tras reintentos: se registra el error; la notificación interna (creada en el paso 6) persiste como canal de registro. |
| &nbsp; | 5 | Sin datos climáticos válidos: fallback de fecha al día siguiente. |
| Rendimiento&nbsp; | Paso&nbsp; | Cota de tiempo&nbsp; |
| &nbsp; | 6&nbsp; | Transacción por maquinaria; sin cota crítica (proceso diario)&nbsp; |
| **Frecuencia**&nbsp; | Diario (umbrales) + cada 4 horas (programados) + tiempo real (odómetro)&nbsp; |  |
| **Estabilidad**&nbsp; | alta&nbsp; |  |
| **Comentarios**&nbsp; | La notificación interna es el canal de registro; el email es canal de aviso adicional. |  |

| PA-02&nbsp; | Análisis climático operativo |  |
| :---- | :---- | :---- |
| **Objetivos asociados**&nbsp; | OBJ-02 Soporte operativo y trazabilidad de la producción forestal; OBJ-03 |  |
| **Requisitos asociados**&nbsp; | RF-18; IRQ-09; UC-61 (validación con override); UC-63 (fecha sin lluvia) |  |
| **Descripción**&nbsp; | El sistema sincroniza automáticamente pronóstico e histórico climático por lote (coordenadas GPS), mapea los días operativos/inactivos con umbrales y recomienda estrategia (anticipación/reacción/normal). El estado persistido alimenta la validación del parte diario y la programación de mantenimientos. |  |
| **Precondición**&nbsp; | Cron del servidor activo; lotes activos con coordenadas; acceso al servicio externo Open-Meteo. |  |
| **Secuencia normal**&nbsp; | **Paso**&nbsp; | **Acción**&nbsp; |
| &nbsp; | 1 | (Cada 6 horas / diario 06:00 / diario 00:30) Las tareas programadas clima:decisiones, clima:analizar y clima:real seleccionan los lotes activos con coordenadas. |
| &nbsp; | 2 | ClimaApiService obtiene el pronóstico (o el histórico real del día anterior, con degradación de fuente: archivo → pronóstico pasado). |
| &nbsp; | 3 | ClimaAnalisisService mapea los días inactivos aplicando umbrales (lluvia 10 mm, nubosidad 60%, viento 15 km/h, ET0 4 mm). |
| &nbsp; | 4 | ClimaPersistenciaService persiste el estado por lote/día con su fuente (api/archive/forecast) y marca de actualización. |
| &nbsp; | 5 | ClimaEstrategiaService determina la estrategia y la recomendación operativa. |
| &nbsp; | 6 | (Demanda) Al cargar un parte diario, ClimaOperativoService::obtenerEstadoDia() lee el registro del día; si el pronóstico no está fresco, sincroniza en el momento. |
| &nbsp; | 7 | El parte diario consulta el estado: si el día es no operativo, exige override motivado del Capataz para continuar. |
| **Postcondición**&nbsp; | Estado climático por lote/día persistido y auditable (incluidos los fallos como registros fallback). |  |
| **Excepciones**&nbsp; | **Paso**&nbsp; | **Acción**&nbsp; |
| &nbsp; | 1 | Lote sin coordenadas: registro fallback con el motivo, sin llamada a la API. |
| &nbsp; | 2 | API externa caída: política fail-open — se asume día operativo, se persiste el error como fallback y se reintenta en la siguiente corrida (sin reintento inmediato). |
| Rendimiento&nbsp; | Paso&nbsp; | Cota de tiempo&nbsp; |
| &nbsp; | 6&nbsp; | Estado del día servido desde registro persistido; sync bajo demanda solo si el pronóstico está vencido&nbsp; |
| **Frecuencia**&nbsp; | Cada 6 horas (decisiones) + diario (riesgo y clima real) + bajo demanda (parte diario)&nbsp; |  |
| **Estabilidad**&nbsp; | alta&nbsp; |  |
| **Comentarios**&nbsp; | El fail-open es una decisión de diseño: el clima asiste la operación, nunca la bloquea por falla técnica propia. |  |

## Diagrama de Interacción

**Operaciones**

Los contratos de operación del nivel de análisis se refinan aquí a diseño. Para los tres procesos automatizados, las operaciones del sistema y sus colaboradores de diseño son:

**Operación: verificarUmbralesMantenimiento()** (PA-01)

- Disparador: tarea programada diaria 06:30 (`routes/console.php`).
- Colaboradores: `CheckMantenimientoUmbrales` (comando, orquestador del proceso) → `Mantenimiento` (creación de la orden), `Empleado` (búsqueda de personal disponible), `KitMantenimientoPreventivo`/`MovimientoStock` (detección de faltantes), `PropuestaCompraMantenimiento` (propuesta de compra), `NotificacionSistema` (canal interno), `MantenimientoDocumentsService` (PDFs), `MantenimientoOrdenGeneradaMail` (email con reintentos), `ClimaDecisionService` (fecha fuera de lluvia).
- En tiempo real: `PartesDiarios` (componente) → `CargaRegistrada` (evento) → `ActualizarOdometroMaquina` (listener) → `Maquinaria` (incremento de odómetro).

**Operación: sincronizarClimaLote(lote)** (PA-02)

- Disparador: tareas programadas (cada 6 horas / diarias) y demanda desde el parte diario.
- Colaboradores: `AnalizarDecisionesClimaticas` / `AnalizarRiesgoClimatico` / `SincronizarClimaReal` (comandos) → `ClimaDecisionService` (orquestador) → `ClimaApiService` (Open-Meteo), `ClimaAnalisisService` (mapeo de días), `ClimaEstrategiaService` (estrategia), `ClimaPersistenciaService` → `ClimaDiaLote` (persistencia con fuente y errores). Consumo: `ClimaOperativoService::obtenerEstadoDia()` desde `PartesDiarios`.

**Operación: generarPropuestasAsignacion(idLote)** (PA-03)

- Disparador: `LoteObserver` (cambio de estado, tras el commit) y guardado de planificación (`LotePlanificacionTareas`).
- Colaboradores: `GenerateAllocationProposalsForLote` / `ProcessAllocationProposal` (jobs únicos e idempotentes) → `AutomaticAllocationService` (experto en propuestas) → `HistoricalTaskPerformanceRepository` (histórico de desempeño), `PropuestaAsignacion` + tablas de candidatos (persistencia), `SendPurchaseOrderEmail` (email idempotente).

## Diagrama de Clase

La arquitectura de clases se organiza en cuatro capas con responsabilidades no compartidas:

**1. Componentes Livewire (interfaz)** — `app/Http/Livewire/`

Interacción con el usuario, validación básica de formularios y comunicación con servicios. Sin reglas de negocio ni acceso directo a base de datos. Ejemplos: `PartesDiarios`, `Mantenimientos`, `AllocationProposals`, `EstadoProcesos` (monitoreo de procesos automatizados: catálogo de procesos, clima por lote y cola de trabajos, leyendo a través de `EstadoProcesosService`).

**2. Servicios (reglas de negocio)** — `app/Services/`

Expertos de dominio (GRASP Information Expert): `MantenimientoService` (ciclo de vida de órdenes), `ClimaDecisionService` + especializados (Api/Análisis/Estrategia/Persistencia/Operativo — Cohesión Alta, cada uno con una razón de cambio), `AutomaticAllocationService` y `PropuestaAsignacionService` (propuestas), `InventarioService` (FIFO), `EmpleadoPagoService` (liquidaciones), `ForestalStatsService` (KPIs), `NotificacionService` (configuración y estados de notificaciones), `EstadoProcesosService` (consultas de monitoreo).

**3. Modelos Eloquent (persistencia)** — `app/Models/`

Relaciones, casts, scopes y accessors/mutators simples. Sin lógica de negocio compleja (excepción documentada: `Empleado::calcularPagoRango()`, experto en el cálculo de su propia liquidación).

**4. Automatización (procesos en segundo plano)** — `app/Console/Commands/`, `app/Jobs/`, `app/Events/`, `app/Listeners/`, `app/Observers/`

- Comandos Artisan: tareas programadas del scheduler (`CheckMantenimientoUmbrales`, `CheckMantenimientosProgramados`, `AnalizarDecisionesClimaticas`, `AnalizarRiesgoClimatico`, `SincronizarClimaReal`) y utilidades operativas de ejecución manual (`AllocationPropose`, `AllocationSendPurchaseOrder`, `MailTest`, `OptimizarSistema`).
- Jobs en cola: `GenerateAllocationProposalsForLote`, `ProcessAllocationProposal` (ambos `ShouldBeUnique` e idempotentes) y `SendPurchaseOrderEmail` (idempotente por metadatos).
- Evento/Listener: `CargaRegistrada` → `ActualizarOdometroMaquina` (odómetro en tiempo real).
- Observer: `LoteObserver` (dispara propuestas ante cambios de estado, con `DB::afterCommit`).

**Relaciones entre capas**: los componentes Livewire delegan en servicios; los comandos orquestan servicios y modelos; el observer y los componentes encolan jobs; el scheduler (`routes/console.php`) dispara los comandos con protección `withoutOverlapping` y registro de fallos/éxitos. La pantalla `EstadoProcesos` permite al Administrador ver el estado de los tres procesos (clima por lote, cola, catálogo) sin exponer detalles técnicos.

**Decisiones de diseño relevantes**

- *Transacción por maquinaria* en la verificación de umbrales: aislamiento de fallos (una maquinaria con error no detiene el proceso).
- *Fail-open climático*: el clima asiste, nunca bloquea por falla técnica propia; el error queda persistido y auditable.
- *Canal interno como registro, email como aviso*: la notificación interna se crea dentro de la transacción; el email es best-effort con reintentos.
- *Idempotencia y unicidad en los jobs*: ni duplicados concurrentes ni regeneración innecesaria del mismo día.
- *Decisión humana final*: las propuestas nunca asignan solas (UC-66); el override climático exige motivación (UC-61); las órdenes generadas se confirman y cierran manualmente (UC-62).
